# ТЗ: оптимизация и упрощение Finn

Дата: 15 сентября 2026 года.  
Статус: план работ; реализация этапов не начата.  
Стек: Go, Gin, SQLite, React, TypeScript, Vite.

## 1. Цель

Снизить вероятность ошибок при изменении финансовых данных, сократить дублирование и сделать интерфейс единообразным. Повышать производительность на основании воспроизводимых замеров.

Работа выполняется последовательно: данные → общие UI-элементы → разделение компонентов → CSS → производительность. Каждый этап должен давать отдельный проверяемый результат.

## 2. Исходное состояние

Перед началом исполнитель читает актуальный код и `git diff`: часть изменений может находиться в рабочем дереве без коммита.

В текущем рабочем дереве уже реализованы:

- Общая сериализация Cash Flow с сохранением `tag` и `toTag` для редактора снапшота и страницы Cash Flow.
- Редактирование комментариев из фида через общий `CommentModal` и отдельный API, меняющий выбранный комментарий.
- Проверка устаревшего комментария или баланса при сохранении из фида.
- Компактные кнопки действий на уровне заголовка карточки фида.
- Курс покупки валюты в Deposit Comparator и выравнивание подписей полей.

Эти изменения необходимо сохранить и использовать как основу. Перед реализацией уточнить их наличие в текущей версии, чтобы не выполнять работу повторно.

## 3. Общие требования

1. Сохранить действующие формулы, правила округления, тэги, комментарии, курсы и время редактирования снапшотов.
2. Сохранить чтение существующей базы, резервных копий и черновиков. Миграции схемы в объём этого ТЗ не входят.
3. Сохранить маршруты, горячие клавиши, управление фокусом, прокрутку и предупреждения о несохранённых изменениях.
4. Переиспользовать существующие компоненты и хуки. Новый общий компонент выделять при наличии конкретных повторяющихся потребителей.
5. Ограничиться текущим стеком и зависимостями. Приводить измеримое обоснование, если для этапа 5 понадобится дополнительная библиотека.
6. Выполнять по одному этапу. Разделять крупный этап на законченные изменения по отдельным экранам или операциям.
7. Агент проверяет типы, логику, сборку и тесты. Визуальную проверку выполняет пользователь; отсутствие этой проверки явно отмечается в отчёте.
8. Для проверок данных использовать тестовые фикстуры и временную SQLite-базу. Производительность измерять на синтетических данных.
9. Не смешивать рефакторинг с изменением продуктового поведения. Обнаруженные посторонние ошибки описывать отдельно.

## 4. Модели и reasoning effort

Назначение моделей — инженерная рекомендация для этого проекта, а не результат сравнительного тестирования моделей на Finn. Выбраны модели, доступные в текущем приложении Codex. `Effort` означает настройку глубины рассуждения; это не оценка длительности работы.

| Этап | Приоритет | Модель | Effort | Обоснование |
| --- | --- | --- | --- | --- |
| 1. Работа с данными | Высокий | `gpt-5.6-sol` | `high` | Нужно проследить загрузку, преобразование и сохранение данных через несколько экранов. |
| 2. Общие UI-элементы | Высокий | `gpt-5.6-terra` | `medium` | Ограниченные изменения существующей разметки и компонентов с конкретными потребителями. |
| 3. Разделение компонентов | Средний | `gpt-5.6-sol` | `high` | Важно сохранить связи состояния, эффекты, зависимости хуков и поведение редакторов. |
| 4. Организация CSS | Средний | `gpt-5.6-terra` | `medium` | Перенос стилей по заранее выделенным областям с сохранением каскада. |
| 5. Производительность | После замеров | `gpt-6-astra` | `high` | Требуется установить причины задержек и сопоставить изменения запросов, расчётов и отображения. |

`medium` и `high` поддерживаются выбранными моделями. Источники: официальные страницы [GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol), [GPT-5.6 Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra) и [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra).

Если этап упирается в непонятную регрессию, сначала сузить воспроизводимый пример и объём изменения. Повышение effort само по себе не заменяет диагностику. Модель и effort этой таблицы относятся к будущему запуску этапа; создание документа не меняет настройки текущей задачи.

## 5. Этап 1 — единая работа с данными

**Модель:** `gpt-5.6-sol` · **Effort:** `high`  
**Зависимости:** исходное состояние из раздела 2.

### Объём работ

1. Составить список операций загрузки и сохранения снапшотов, комментариев и Cash Flow и найти все их потребители.
2. Выделить общую функцию JSON-запросов: проверка HTTP-статуса, разбор ответа, сообщение сервера и понятная ошибка при не-JSON ответе. При необходимости поддержать отмену через `AbortSignal`.
3. Вынести предметные операции в модули API, например `snapshotsApi.ts` и `cashFlowApi.ts`. Обработчики UI должны вызывать именованные операции.
4. Объединить повторяющуюся нормализацию Cash Flow. Использовать существующую общую сериализацию при сохранении периода.
5. Сохранить различие между исходными данными сервера и курсами, нормализованными для отображения. Редактирование комментария должно продолжать использовать существующий точечный API.
6. Унифицировать обработку сохранения: блокировка повторного запроса, сохранение введённого текста при ошибке, обновление локального состояния после успеха.

Основные места: `useSnapshots`, `useFlowEntries`, `SnapshotEdit`, `CashFlow`, `CommentFeed`, `useSnapshotEditorData`, `lib/cashFlow.ts`.

### Критерии приёмки

- [ ] В перечисленных потребителях каждая предметная операция использует общую реализацию API.
- [ ] Ошибки загрузки и сохранения не воспринимаются как успешный ответ или пустой набор данных.
- [ ] Сохранение и копирование периода сохраняют явные тэги; выбор Auto по-прежнему позволяет очистить тэг.
- [ ] Сохранение комментария меняет нужную строку, включая несколько балансов одной валюты, и сохраняет остальные данные.
- [ ] Ошибка или конфликт оставляет текст в редакторе; успешное сохранение обновляет текущий экран.
- [ ] Существующие регрессионные тесты проходят; новые тесты добавлены для изменённых сценариев ошибок и преобразования данных.

Общее межстраничное кеширование данных относится к этапу 5: на этом этапе достаточно объединить операции и преобразования.

## 6. Этап 2 — общие UI-элементы

**Модель:** `gpt-5.6-terra` · **Effort:** `medium`  
**Зависимости:** этап 1.

### Объём работ

1. Ввести именованные размеры кнопок: обычная, компактная, кнопка с иконкой. Использовать существующую `.btn` как основу.
2. Выделить заголовок карточки с названием, необязательными бейджами и группой действий. Начать с карточек фида и предложений калькуляторов.
3. Сохранить компактные действия фида: кнопки находятся в строке заголовка; текст комментария занимает ширину под ним.
4. Объединить повторяющиеся стили подписей, подсказок и полей калькуляторов. У подписей с подсказкой и без неё должна совпадать высота.
5. Вынести общие элементы калькуляторов в отдельный модуль, чтобы этап 3 мог импортировать их без зависимости от остальных калькуляторов.
6. Показать варианты общих элементов в существующем StyleLab, если они требуют визуального сравнения.

### Критерии приёмки

- [ ] Размеры и отступы кнопок в затронутых экранах задаются общими вариантами.
- [ ] Заголовок карточки имеет минимум двух реальных потребителей без большого набора специальных флагов.
- [ ] Сохранены состояния disabled/loading, доступные названия кнопок и управление с клавиатуры.
- [ ] Редакторы комментариев продолжают использовать общий `CommentModal`.
- [ ] Пользователю передан короткий список экранов для проверки обычной и узкой ширины, длинных названий и тэгов.

Редизайн остальных страниц и массовая замена всех кнопок приложения в этот этап не входят.

## 7. Этап 3 — разделение крупных компонентов

**Модель:** `gpt-5.6-sol` · **Effort:** `high`  
**Зависимости:** этапы 1–2.

### Объём работ

Выполнять в следующем порядке, сохраняя рабочую сборку после каждого подпункта:

1. **Калькуляторы.** Разделить `FinancialCalculatorModals.tsx` на файлы отдельных калькуляторов и общие элементы. Математику оставить в `lib/financialCalculators.ts`. Сохранить настройки, значения по умолчанию, выбор валют и загрузку данных снапшота.
2. **Фид.** Вынести построение событий, группировку по периодам и правила highlights в чистые функции. Выделить карточку события и хук редактирования комментария.
3. **SnapshotEdit.** Сначала использовать имеющиеся `useSnapshotDraft` и `useSnapshotEditorData`. Отделить оставшуюся работу с Cash Flow и обработчики редактора там, где есть самостоятельная ответственность.
4. **CashFlow.** Выделить самостоятельные блоки отображения и операции редактора периода, сохранив общую модалку и API этапа 1.

Страницы связывают данные, состояние и действия. Чистые расчёты не зависят от React и браузерного DOM.

### Критерии приёмки

- [ ] Выделенные компоненты имеют понятные props, а хуки — ограниченную ответственность.
- [ ] Данные не дублируются в нескольких независимых состояниях без необходимости.
- [ ] Сохранены восстановление черновиков, подтверждение выхода, горячие клавиши и фокус.
- [ ] Порядок и состав событий фида совпадают с исходным поведением на фиксированных данных.
- [ ] Калькуляторы дают прежние результаты, включая ручной курс покупки и курс погашения.
- [ ] Существующие тесты сохранены; для выделенных правил фида добавлены проверки пользовательских сценариев.

Сокращение количества строк в файле не является самостоятельным критерием приёмки.

## 8. Этап 4 — организация CSS

**Модель:** `gpt-5.6-terra` · **Effort:** `medium`  
**Зависимости:** этапы 2–3.

### Объём работ

1. Разделить стили на глобальные основы и предметные области: снапшоты, Cash Flow, фид, графики, инструменты.
2. Оставить в глобальных стилях тему, базовые элементы и общие варианты UI этапа 2.
3. Переносить стили небольшими группами, сохраняя порядок правил, специфичность и media queries.
4. Перевести повторяющиеся статические inline-стили затронутых компонентов в классы. Динамические цвета и вычисляемые значения оставить там, где они нужны.
5. Удалять дубли и неиспользуемые правила только после проверки потребителей, включая порталы, ленивые маршруты и StyleLab.

### Критерии приёмки

- [ ] У каждой перенесённой группы стилей понятный владелец и место подключения.
- [ ] Сохранены адаптивность, тема, порядок наложения модалок и тултипов.
- [ ] Последовательность открытия страниц не влияет на их оформление.
- [ ] Общие стили полей и кнопок не продублированы в файлах отдельных страниц.
- [ ] Подготовлен список затронутых экранов и состояний для визуальной проверки пользователем.

Целевой размер `index.css` не задаётся: важны понятные границы и отсутствие регрессий каскада.

## 9. Этап 5 — производительность по замерам

**Модель:** `gpt-6-astra` · **Effort:** `high`  
**Зависимости:** этапы 1–4 и исходные замеры перед изменениями производительности.

### 9.1. Подготовить воспроизводимую базу сравнения

Создать детерминированные синтетические наборы. Числа ниже — размеры фикстур, а не заявленные объёмы реальных пользователей:

| Набор | Снапшоты | Организации на снапшот | Балансы на организацию | Всего движений Cash Flow |
| --- | ---: | ---: | ---: | ---: |
| Малый | 12 | 5 | 3 | 200 |
| Средний | 60 | 20 | 5 | 5 000 |
| Большой | 120 | 40 | 8 | 20 000 |

Зафиксировать версии среды, оборудование, режим production, параметры фикстуры и метод измерения. Отдельно учитывать холодную загрузку и повторное открытие. Для каждого сценария делать не менее пяти запусков и сравнивать медианы.

Измерять:

- время формирования итогов, аналитики и событий фида;
- время и объём ответов API, количество повторяющихся запросов;
- размеры загружаемых JavaScript-модулей;
- время открытия дашборда, фида, графиков и реакцию редактора на ввод — по браузерным замерам пользователя;
- объём памяти, если выбранное решение добавляет кеширование.

Агент готовит скрипты для алгоритмов и API, а для браузерных измерений — короткую инструкцию пользователю. Отсутствующие браузерные замеры отмечаются как неподтверждённые результаты.

### 9.2. Устранить подтверждённые узкие места

В зависимости от результатов выбрать минимальное достаточное изменение:

- Общее хранение загруженных данных и объединение одинаковых запросов; предусмотреть обновление после записи, импорта и SQL-редактирования.
- Переиспользование вычисленных итогов с корректными зависимостями от валюты, периода, снапшотов и Cash Flow.
- Ограничение числа одновременно отображаемых строк при подтверждённой задержке больших списков; сохранить поиск, фокус и переход к нужной записи.
- Пересмотр загрузки маршрутов и калькуляторов, если разбор JavaScript заметно влияет на открытие экрана.
- Оптимизация конкретных SQL-запросов на основании их плана выполнения и измерений.

Текущие крупные application chunks выбраны намеренно для локальной работы; сам размер модуля не является достаточной причиной его дробить.

### Критерии приёмки

- [ ] Есть воспроизводимые данные, команды и таблица результатов до/после.
- [ ] Для каждого изменения названы узкое место, выбранная метрика и численный результат.
- [ ] Цель улучшения зафиксирована после исходного замера и до реализации; выигрыш превышает разброс измерений.
- [ ] Финансовые результаты на одинаковых данных совпадают с исходными результатами.
- [ ] При добавлении кеша проверены обновление после записи и отсутствие устаревших данных.
- [ ] Заметное ухудшение на малом наборе или рост памяти явно отражены в отчёте.
- [ ] Если значимых задержек не обнаружено, результат этапа — отчёт и инструменты измерения; изменения приложения не обязательны.

## 10. Проверки и отчёт по каждому этапу

Для frontend запускать из `frontend/`:

```sh
npm test
npm run build
npm run lint
```

При изменении backend/API запускать из корня репозитория:

```sh
go test ./...
```

Дополнительно проверять `git diff --check`. Тесты должны проверять поведение и сохранность данных. Для простого переноса CSS отдельные тесты, повторяющие текст реализации, не нужны.

Отчёт исполнителя содержит:

1. Выполненный этап и его границы.
2. Что изменилось и какие дубли устранены.
3. Выполненные проверки и их результаты.
4. Пункты ручной проверки UI для пользователя.
5. Оставшиеся ограничения и обнаруженные вопросы вне объёма этапа.
6. Для этапа 5 — измерения до/после и команды воспроизведения.

Автоматические проверки и визуальная приёмка отмечаются отдельно. Реализация ТЗ не включает публикацию релиза.
